# Оптимизация и устранение дублирования кода

Документ описывает, какие фрагменты кода в проекте повторяются (или почти повторяются) и как их
можно объединить. Цель — меньше дублирования, проще сопровождение и правки в одном месте.
Это план, а не обязательное к исполнению: каждый пункт можно применять по отдельности.

Общий принцип: выносить повторяющиеся куски в **небольшие именованные функции-помощники**
(на уровне файла или класса). Это не меняет поведение, но убирает копипаст.

## 1. Вычисление «клетка по пикселю» (`tileOf`)

**Где:** `map-painter.js`, три почти одинаковых замыкания:

* строка 879: `const tileOf = k => Math.floor(k / W / T) * size + Math.floor((k % W) / T);`
* строка 1360: `const tileOf = k => Math.floor(Math.floor(k / W) / T) * size + Math.floor((k % W) / T);`
* строка 1842: `const tileOf = k => Math.floor(Math.floor(k / W) / T) * size + Math.floor((k % W) / T);`

Плюс та же формула «запасного варианта» встречается в `buildCellMap` (строка 2691).

**Проблема:** четыре копии одной формулы; первая к тому же записана иначе (`k / W / T` вместо
`Math.floor(k / W) / T`) и даёт верный результат только потому, что `W` делится на `T`. Если
поменять `tileSize`/размер, поведение копий может разойтись.

**Предложение:** один метод класса:

```js
// индекс клетки, которой принадлежит пиксель k
tileOf(k) {
    const x = k % this.width;
    return Math.floor((k - x) / this.width / this.tileSize) * this.map.size
         + Math.floor(x / this.tileSize);
}
```

и заменить все четыре места на `this.tileOf(k)`.

Выгода: одна формула, нет риска расхождения, короче код.

## 2. Функции-помощники `n(value)` и `rnd(n)`

**Где:** `map-painter.js`, локальные замыкания, объявленные заново в каждом методе:

* `const n = value => Math.max(1, this.px(value));` — строки **1948**, **2212**, **2273**
* `const rnd = n => hashUnit(x, y, 1000 + n);` — строка **1947** (в `layoutSettlement`)

**Проблема:** одинаковая мелкая функция объявляется три раза; смысл («минимум 1 пиксель для
клетки 12×12») разъехался бы при правке в одном месте.

**Предложение:** один метод класса:

```js
// «пиксели для клетки 12×12», но не меньше 1
pxMin(n) {
    return Math.max(1, this.px(n));
}
```

`rnd` завязан на `(x, y)` конкретной клетки, поэтому его разумно оставить локальным, но можно
ввести и общий `tileRandom(x, y, n)`, если им начнут пользоваться другие методы.

## 3. `linePoints` продублирован целиком

**Где:** алгоритм Брезенхэма реализован дважды, почти посимвольно одинаково:

* `map-painter.js:411` — `linePoints(x0, y0, x1, y1)`
* `sprite-renderer.js:236` — `linePoints(x0, y0, x1, y1)` (только округляет входные координаты)

**Проблема:** два экземпляра одного алгоритма; правка (например, толщина или оптимизация)
должна вноситься в оба.

**Предложение:** оставить одну реализацию на уровне файла (например, в `map-painter.js`, откуда
`sprite-renderer.js` уже берёт функции цвета) и вызывать её из обоих мест:

```js
function linePoints(x0, y0, x1, y1) { /* Брезенхэм, округление внутри */ }
```

`sprite-renderer.js` при этом просто перестаёт определять свой метод.

Выгода: один алгоритм; `sprite-renderer.js` уже зависит от `map-painter.js`, новых зависимостей
не появляется.

## 4. Проверка «пиксель свободен» (`usable`)

**Где:** `map-painter.js` — одна и та же проверка «не вода, не река, не высокие горы» повторяется:

* строка 1658: `if (this.waterMask[k] || (this.riverMask && this.riverMask[k])) return;`
* строка 1879: `if (this.waterMask[k] || (this.riverMask && this.riverMask[k]) || (relief && relief[k] > 40)) continue;`
* строка 1960: `return !this.waterMask[k] && !(this.riverMask && this.riverMask[k]) && !(this.reliefHeight && this.reliefHeight[k] > 40);`
* строка 2054: `const usable = k => !this.waterMask[k] && !(this.riverMask && this.riverMask[k]) && !(relief && relief[k] > 40);`
* строка 2978 (`wet`) и 1428 — близкие варианты.

**Проблема:** одно и то же условие «где можно рисовать» в пяти местах, причём в двух формах
(через `||`-return и через `!`-предикат). Порог `40` (высота гор) — «магическое число»,
продублированное.

**Предложение:** один метод-предикат и вынести порог в константу/опцию:

```js
// можно ли рисовать в пикселе k (не вода, не река, не высокие горы)
freeGround(k) {
    if (this.waterMask[k]) return false;
    if (this.riverMask && this.riverMask[k]) return false;
    if (this.reliefHeight && this.reliefHeight[k] > this.solidGroundMaxHeight) return false;
    return true;
}
```

где `solidGroundMaxHeight = 40` — обычная опция в `options`.

**Осторожно:** строка 1879 в дорогах использует локальную переменную `relief = this.reliefHeight`
(может быть `null`), а строка 1428 — другую логику (`level > mask[k]`), её объединять не нужно.
Пункт касается только четырёх «однотипных» мест.

## 5. Обход соседей (8 и 4 направления)

**Где:** циклы `for (let dy = -1; dy <= 1; dy++) for (let dx = -1; dx <= 1; dx++)` встречаются
7 раз в `map-painter.js` (строки 570, 609, 909, 1279, …) и 3 раза в `map-generator.js`
(строки 520, 929, 1522), каждый раз с ручной проверкой границ и пропуском центра.

Отдельно: `neighbors(i)` и `neighbors8(i)` в `map-generator.js` — родственные методы, но с
разными сигнатурами (`neighbors` возвращает индексы, `regionNeighbors` — плоский список
`[клетка, длина шага, …]`).

**Проблема:** много копий одного обхода, где легко забыть пропустить центр или проверить
границы. В горячих циклах пиксельного рисования создавать массивы нельзя, поэтому там цикл
уместен — но и в них дублируется логика границ.

**Предложение, поэтапно:**

* В **не горячих** местах (логика генератора, подготовительные проходы) использовать готовые
  `neighbors8(i)` / `neighbors(i)` вместо ручных циклов.
* Для **горячих** мест оставить циклы, но вынести проверку границ в крошечные inline-хелперы
  или таблицу смещений, чтобы не дублировать `nx >= 0 && ny >= 0 && …`.
* Рассмотреть таблицу смещений 8 направлений и общий итератор «для каждого валидного соседа».

**Осторожно:** буферы наподобие `const around = new Int32Array(4)` (строка 869) нужны именно
затем, чтобы не создавать массивы в цикле — их менять не стоит.

## 6. Волновой обход (BFS) — один и тот же каркас

**Где:** в `map-generator.js` пять раз повторяется каркас «очередь + `head` + push соседей»:
`removeSmallMountains` (441), `collectLandComponent` (476), `computeWaterDepth` (497),
`tilesNearMountains` (666), озёра в `fillDepressions` (783). В `map-painter.js` —
дважды (929, 1490).

Каждый раз: создать `queue = [start]`, `visited[start] = 1`, затем
`for (let head = 0; head < queue.length; head++)` и перебор соседей с проверкой условия.

**Проблема:** структурно одинаковый обход с разными условиями «годится ли сосед» и разными
побочными действиями.

**Предложение:** общий помощник с колбэком:

```js
// Обход в ширину от набора стартов. isOpen(j) — годится ли клетка; visit(j) — что сделать при входе в неё.
flood(startTiles, { isOpen, enter, useEight = false }) {
    const seen = new Uint8Array(this.terrain.length);
    const queue = [];
    for (const s of startTiles) { seen[s] = 1; queue.push(s); enter && enter(s, 0); }
    for (let head = 0; head < queue.length; head++) {
        const current = queue[head];
        for (const j of (useEight ? this.neighbors8(current) : this.neighbors(current))) {
            if (seen[j] || !isOpen(j, current)) continue;
            seen[j] = 1;
            enter && enter(j, current);
            queue.push(j);
        }
    }
    return queue;
}
```

Тогда:

* `collectLandComponent` → `flood([start], { isOpen: j => this.isLand(j) })`
* `computeWaterDepth` → старты — все клетки суши, `useEight: true`, в `enter` записываем глубину
* `tilesNearMountains` → старты — горы, `enter` пишет `reach[j] = reach[parent] + 1`
* `removeSmallMountains` / озёра → старты — найденная клетка, `isOpen` проверяет нужный рельеф

**Осторожно:** `computeWaterDepth` и `tilesNearMountains` используют `enter` с родителем и
дополнительную «дальность» — значит, колбэк должен получать и родителя (в примере это
`enter(j, current)`). Это самый крупный по эффекту, но и самый трудоёмкий пункт; применять
по одному обходу за раз.

## 7. Паттерн «кэш по подписи»

**Где:** `map-painter.js` — почти каждый дорогой расчёт хранится в поле-кэше с проверкой
подписи. Видно по `cache && cache.source === …` (8 мест) и по конструкциям вида:

* `paintHills`: `this.hillShading = { source, key, shading }`
* `buildHillHeights`: `this.hillCache = { source, tileSize, height }`
* `buildReliefHeights`: `this.reliefCache = { source, tileSize, sharpness, detail, ragged, zone, height, smooth }`
* `buildRiverGeometry`: `this.riverCache = { source, key, … }`
* `buildRoadGeometry`: `this.roadCache = { source, key, riverMask, … }`
* `buildFog`: `this.fogCache = { source, tileSize, salt, fog }`
* `buildPixelRegions`: `this.regionPixelCache`
* `settlementLayout`: `this.settlementLayoutCache`

**Проблема:** один и тот же приём («сравнить подпись — вернуть кэш — иначе посчитать и
сохранить») продублирован ~8 раз, каждый со своим перечнем полей подписи. Легко забыть поле
(например, при добавлении опции) — и получить устаревшую картинку.

**Предложение:** маленький помощник класса:

```js
// Вернуть кэш, если его подпись совпадает с ожидаемой; иначе посчитать и сохранить.
cached(name, signature, build) {
    const key = JSON.stringify(signature);
    const entry = this[name];
    if (entry && entry.key === key) return entry.value;
    const value = build();
    this[name] = { key, value };
    return value;
}
```

Использование:

```js
const fog = this.cached('fogCache',
    [this.tileSize, this.seedSalt, map.elevation],
    () => { /* расчёт тумана */ });
```

**Осторожно:** в качестве части подписи некоторые методы используют **ссылки** на массивы
(`map.elevation`, `map.terrain`, `map.river`). `JSON.stringify` доступается до содержимого —
нельзя сериализовать большие типизированные массивы. Поэтому для подписи можно оставить
хеш-«отпечаток» (например, ссылку на массив + соль), а не сам массив. Простой безопасный
вариант: держать подпись строкой, а «ссылочные» части сравнивать по ссылке, как сейчас.
Если это усложняет — оставить как есть, а выигрыш ограничить пунктами 1–4.

## 8. Паттерн «ленивый кэш-словарь спрайтов»

**Где:** `map-painter.js`, одна и та же тройка строк в начале трёх методов:

* строка 2114 (`houseSprite`): `if (!this.spriteCache) this.spriteCache = new Map();`
* строка 2207 (`oreSprite`): то же
* строка 2268 (`etherSprite`): то же

Плюс одинаковый каркас «построить ключ → `get` → если есть, вернуть → иначе нарисовать →
`set` → вернуть» (строки 2115–2161, 2208–2244, 2269–2316).

**Предложение:**

* Инициализировать `this.spriteCache = new Map()` один раз в `paint()` рядом с
  `this.shadeCache` / `this.tuftCache` (строки 340–341) и убрать три ленивые инициализации.
* При желании вынести общий каркас в `sprite(kindKey, build)`:

```js
sprite(key, build) {
    const cached = this.spriteCache.get(key);
    if (cached) return cached;
    const value = build();
    this.spriteCache.set(key, value);
    return value;
}
```

Выгода: нет трёх копий проверки `if (!this.spriteCache)`, единый способ кэшировать спрайт.

## 9. `centerOf` и `stamp` для полос (реки, дороги)

**Где:** `map-painter.js`:

* `buildRiverGeometry` (1416): `const centerOf = tile => [x*T + T/2 + (hashUnit(x,y,983)-0.5)*wobble, …]`
* `buildRoadGeometry` (1869): `const centerOf = (x, y) => [x*T + T/2 + (hashUnit(x,y,980)-0.5)*wobble, …]`
* `paintCrossing` (2965): тот же расчёт центра клетки с солями 983/984.

То есть **три раза** повторяется «центр клетки плюс случайное смещение wobble с разными
солями». Аналогично `stamp(...)` для рисования «пера» полосы определён дважды
(строки 1420 и 1873) плюс третий `stamp` в `smoothPixelRegions` (2442).

**Проблема:** формулы центра клетки и «штампа» полосы дублируются, но с разными солями и
разными побочными действиями.

**Предложение:**

* Вынести расчёт центра клетки в метод:

```js
// центр клетки плюс детерминированное смещение (чтобы русла и дороги петляли)
cellCenter(tile, saltX, saltY) {
    const x = tile % this.map.size, y = Math.floor(tile / this.map.size);
    const wobble = this.px(2);
    return [x * this.tileSize + this.tileSize / 2 + (hashUnit(x, y, saltX) - 0.5) * wobble,
            y * this.tileSize + this.tileSize / 2 + (hashUnit(x, y, saltY) - 0.5) * wobble];
}
```

(соли передавать снаружи, чтобы реки и дороги не смещались одинаково).

* `stamp` оставить локальным: его побочные действия (`mask`, `core`/`halo`) слишком разные, и в
  горячем цикле важна простота. Но можно вынести общий «перебор пикселей круга» в маленький
  итератор `forEachInDisc(cx, cy, radius, fn)`.

**Осторожно:** у рек «перо» круглое, у дорог — квадратное, а у `smoothPixelRegions` — список
смещений круга. Полное объединение сделает код менее понятным; выгоднее ограничиться общим
расчётом центра (он действительно одинаков).

## 10. Фильтры «пустая клетка» в текстуре и декоре

**Где:** `map-painter.js` — повторяющиеся условия «клетка не занята»:

* `paintGroundDetail` (1606): `terrain !== PLAIN || biome !== GRASSLAND || river || resource === SETTLEMENT || roadLevel > 0`
* `paintTufts` (1619): `terrain !== PLAIN || river || shore === BEACH || resource === SETTLEMENT || roadLevel > 0`
* `collectProps` (1765): `terrain !== PLAIN || river || resource !== NONE || roadLevel > 0`

**Проблема:** три похожих, но не одинаковых «стоп-условия». Общая часть (не вода/равнина, не
река, не дорога, не поселение) дублируется.

**Предложение:** базовый предикат + частные надстройки:

```js
// клетка свободна для мелкой детали: равнина, без реки, дороги и поселения
hasFreeGround(i) {
    const map = this.map;
    return map.terrain[i] === Terrain.PLAIN && !map.river[i]
        && map.resource[i] !== Resource.SETTLEMENT && map.roadLevel[i] === 0;
}
```

Далее:

* `paintGroundDetail` добавляет `map.biome[i] === Biome.GRASSLAND`
* `paintTufts` добавляет `map.shore[i] !== Shore.BEACH`
* `collectProps` добавляет `map.resource[i] === Resource.NONE && map.shore[i] !== Shore.BEACH`

Выгода: общая часть в одном месте; отличия видны явно.

## 11. Разбор направления дороги

**Где:** «из клетки в клетку → индекс направления» повторяется:

* `map-generator.js:836` (`placeRiverCrossings`): `const direction = (from, to) => [dx, dy]`
* `map-generator.js:1567` (`carveRoad`): `const direction = (from, to) => ROAD_DIRECTIONS.findIndex(...)`
* `map-painter.js:1842`/`1888` и `crossingDirections` — тот же перебор бит `roadLinks` и
  `ROAD_DIRECTIONS`.

**Проблема:** одно и то же преобразование «смещение между клетками ↔ направление» реализовано
несколько раз, в двух формах (вектор и индекс).

**Предложение:** методы класса:

```js
// смещение (dx, dy) между двумя клетками
stepBetween(from, to) {
    const size = this.size;
    return [(to % size) - (from % size), Math.floor(to / size) - Math.floor(from / size)];
}

// индекс направления 0..7 (или -1), соответствующего смещению
directionIndex(from, to) {
    const [dx, dy] = this.stepBetween(from, to);
    return ROAD_DIRECTIONS.findIndex(([ax, ay]) => ax === dx && ay === dy);
}
```

и использовать их в `placeRiverCrossings`, `carveRoad`, `crossingDirections`.

## 12. Повторяющиеся обвязки-сеттеры в `MapRenderer`

**Где:** `map-renderer.js` — шесть сеттеров повторяют один и тот же каркас
`«обновить поле → rebuildBuffer() → draw()»`:

```
setView (65), setSeason (71), setMood (79), setShowSettlements (85),
setShowBorders (91), setShowGrid (99)
```

**Проблема:** каждый сеттер — три-четыре строки почти одинакового кода; забыть `draw()` в
одном из них легко.

**Предложение:** один закрытый помощник:

```js
// Изменить состояние, перерисовать буфер и экран.
apply(change) {
    change();
    this.rebuildBuffer();
    this.draw();
}
```

Тогда:

```js
setMood(mood) { this.apply(() => { this.mood = mood; }); }
setView(view) { this.apply(() => { this.view = view; }); }
```

`setShowGrid` и `refresh` отличаются (строят слой/сбрасывают выделение) — их оставить
как есть или добавить параметры.

Выгода: единый порядок «изменил → перерисовал → показал».

## 13. Ручное построение объекта-сводки в `getTileInfo` / `getRegionInfo`

**Где:** `map-generator.js` — `getTileInfo` (1615) вручную собирает объект из ~16 полей;
`getRegionInfo` (1585) — из ~10 полей. В `main.js` есть парные функции-описатели
`describeTile` / `describeRegion`, которые снова перечисляют те же поля и справочники
(`TERRAIN_NAMES`, `BIOME_NAMES`, `RESOURCE_NAMES`).

**Проблема:** состав полей «сводки» продублирован в двух местах (генератор и `main.js`), и
правится в двух местах при добавлении поля. Справочники имён ресурсов есть и в `ResourceInfo`
(`map-generator.js`), и в `RESOURCE_NAMES` (`main.js`).

**Предложение:**

* Использовать `ResourceInfo[...].name` из `map-generator.js` в `RESOURCE_NAMES` вместо
  отдельного массива в `main.js` (там уже есть имена ресурсов).
* Если `describeTile`/`describeRegion` станут сложнее — вынести форматирование в сами
  `getTileInfo`/`getRegionInfo` (или в отдельный модуль форматирования), чтобы состав полей
  описывался один раз.

**Осторожно:** это вопрос удобства, а не ошибки; важнее не «сломать» существующий текст в
интерфейсе.

## 14. Общий порядок применения

От самого безопасного и выгодного к более трудоёмкому:

1. **Пункты 1, 2** (`tileOf`, `n`/`pxMin`) — механическая замена, поведение не меняется.
2. **Пункт 3** (`linePoints`) — удалить дубликат, вызвать общий.
3. **Пункты 4, 10** (`freeGround` / `hasFreeGround`) — собрать общие условия, порог 40 — в опцию.
4. **Пункт 8** (ленивый кэш спрайтов) — одна инициализация в `paint()`.
5. **Пункт 12** (`apply`) — единый сеттер в `MapRenderer`.
6. **Пункт 11** (`stepBetween` / `directionIndex`).
7. **Пункт 9** (общий `cellCenter`).
8. **Пункты 5, 6** (обход соседей и BFS) — самые крупные; делать по одному обходу за раз,
   обязательно проверяя результат генерации на нескольких seed-ах.
9. **Пункт 7** (кэш по подписи) — только если получится решить вопрос со ссылками на массивы;
   иначе оставить как есть.
10. **Пункт 13** — по желанию, ради порядка.

### Как проверять, что ничего не сломалось

* Прогонять одну и ту же карту (один `seed`) до и после правки и **сравнивать результат**:
  для «чистого» рефакторинга логики удобно сравнивать массивы (`terrain`, `regionId`, `river`)
  по хешу; для рисования — сравнивать полученный холст (например, сумму пикселей или
  попиксельное сравнение).
* Проверять не только один seed, но и несколько разных, а также зимний и тёмный режимы
  (они включают дополнительный код: лёд, снег, цветокоррекцию, мрачные детали).

### Что объединять НЕ стоит

* Горячие пиксельные циклы (фон, рельеф, реки) — здесь важна скорость и последовательный
  доступ к памяти; лишние вызовы функций и создание массивов в цикле замедлят рисование.
  Разумный компромисс: вынести повторяющиеся куски в отдельные **именованные функции с
  простыми аргументами** (как уже сделано с `computeHillShading` и `applyHillShading`), но
  не вводить объекты и замыкания в самом внутреннем цикле.
* Части с сильно разными побочными действиями (`stamp` у рек/дорог/сглаживания регионов) —
  формально похожи, но объединение сделает код запутаннее.
